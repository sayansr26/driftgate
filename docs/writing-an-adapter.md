# Writing an adapter

An adapter teaches Driftgate one tool: which files that tool reads, in what order, how to
render canonical rules into its format, and how to read that format back. It is a pure
module — `{ name, apiVersion, detect, read, write, docs }` — that returns artifacts and
never touches the disk.

This guide is the long form. [`docs/adapter-api-v1.md`](adapter-api-v1.md) is the normative
contract and the short version; read it too, but you can write an adapter from this page.

Budget: a concatenated-Markdown tool is an afternoon, most of it spent reading the vendor's
documentation rather than writing TypeScript. The scaffold writes the TypeScript.

## 0. Before you start

Answer three questions from the tool's own documentation, and write the answers down — they
become `src/docs.ts`, which is the part of an adapter that has value beyond this repository.

1. **Which files does the tool read?** All of them: project, nested, user-level.
2. **What happens when two of them apply?** Does the nearest one _replace_ the others
   (`override`), or are they all sent (`additive`)? Getting this backwards makes
   `driftgate doctor` lie.
3. **What is the format?** Plain Markdown, Markdown with frontmatter, or something that
   merely resembles a format you know. Assume nothing here; see §2.

If the tool has no published documentation for its config files, say so in the issue and
stop. Driftgate's precedence data carries a source URL and a verified-against version for
every claim, and a guess cannot have one.

## 1. Scaffold

From a checkout of this repository:

```bash
driftgate adapter new kiro          # prints the plan; writes nothing
driftgate adapter new kiro --yes    # applies it
pnpm install && pnpm test           # green as generated
```

The id must be lowercase kebab-case (`kiro`, `roo-code`). The command refuses if the id is
already registered, if any file it would create exists, or if you are not in a checkout of
this monorepo — all checked before the first write, so a collision leaves the tree untouched.

It **creates** twelve files:

```
packages/adapters/<tool>/package.json
packages/adapters/<tool>/tsconfig.json
packages/adapters/<tool>/src/index.ts        # a working concatenated-Markdown adapter
packages/adapters/<tool>/src/docs.ts         # precedence data, all placeholders
packages/adapters/<tool>/test/{detect,write,read}.test.ts
fixtures/<tool>/{input,expected}             # the write golden
fixtures/<tool>-detect/{positive,negative}   # detection
fixtures/<tool>-import/{input,expected}      # the read golden
```

and **patches** four:

| File                                     | Why                                                                        |
| ---------------------------------------- | -------------------------------------------------------------------------- |
| `packages/cli/src/registry.ts`           | `ADAPTERS` is the roster the CLI runs                                      |
| `packages/cli/package.json`              | the CLI depends on each adapter package                                    |
| `vitest.config.ts`                       | without the alias, tests resolve through `exports` into an unbuilt `dist/` |
| `docs/rfc-0001-canonical-format.md` §4.1 | the table of valid tool ids                                                |

Registration is part of the scaffold rather than a follow-up step because
`packages/cli/test/registry.test.ts` asserts that `ADAPTERS` equals the directory listing of
`packages/adapters/`. An unregistered adapter fails the suite instead of quietly going
unused.

What the scaffold cannot know is the artifact path, the real precedence rules, and what the
tool's format actually looks like. That is the rest of this guide.

## 2. Write the golden first

**Hand-write `fixtures/<tool>/expected/` from the vendor's documentation before you touch
`write()`.** This is the single most load-bearing convention in the project, and it is not
about discipline — a golden generated by the adapter it exists to check proves only that
the adapter agrees with itself.

Both format traps this project has hit were caught this way, and neither would have been
caught otherwise:

- **Cursor's `.mdc` looks like YAML and is not.** `globs` is a bare comma-joined string, an
  empty `globs` is a bare key, and `alwaysApply` is derived rather than authored. A YAML
  emitter produces plausible output that Cursor reads differently.
- **Copilot's `.instructions.md` frontmatter _is_ YAML, and the mistake is treating it like
  YAML.** `applyTo` is one quoted string with the patterns comma-separated _inside_ it. An
  emitted YAML sequence parses cleanly and matches nothing.

The scaffold puts a generated golden there so the suite is green on arrival. Replace it.
The input side (`fixtures/<tool>/input/`) is a small `.driftgate/` — a manifest and three
rules, one of them scoped to another tool — and rarely needs changing.

## 3. `detect`

```ts
async function detect(ctx: AdapterContext): Promise<DetectResult> {
  const evidence: string[] = [];
  for (const path of DETECTION_PATHS) {
    if (await ctx.fs.exists(path)) evidence.push(path);
  }
  return detected(evidence);
}
```

`DetectResult` is `{ detected: boolean, evidence: readonly string[] }`, and `detected()`
sorts the evidence and sets the flag. The evidence is not decoration: `doctor` has to be
able to say _why_ it believes a tool is in use, and "detected Cursor" with nothing behind it
is exactly the unfalsifiable output `doctor` exists to replace.

Detect on things a user of that tool really has — its config directory, its instruction
file — and nothing that another tool also creates.

The two fixture repos under `fixtures/<tool>-detect/` are whole repositories, usually
without a `.driftgate/` at all, because `detect()` runs on repositories that have not
adopted Driftgate. `positive/` must be detected, `negative/` must not.

## 4. `write`

```ts
async function write(ctx: AdapterContext): Promise<readonly Artifact[]> {
  const { canonical } = ctx;
  if (isCanonicalSource(canonical.manifest, TOOL_MD)) return [];

  const rules = sortRules(canonical.rules.filter((r) => selects(r.frontmatter.tools, 'tool')));
  if (rules.length === 0) return [];

  const body = renderConcatenated(rules, { headingLevel: 2, showGlobs: true });

  return [
    finalizeArtifact({
      path: TOOL_MD,
      contents: withHtmlMarker(body, canonical.manifest.options.marker),
      adapter: 'tool',
      kind: 'rules',
      provenance: { ruleIds: rules.map((r) => r.id) },
    }),
  ];
}
```

Four rules govern this function:

- **It returns artifacts; it does not write them.** `AdapterContext.fs` is a
  `ReadOnlyFileSystem`. Note what is absent from the context: no writer, no network client,
  no process spawner. This is what makes `check` and `sync` structurally incapable of
  disagreeing — both consume one rendering pass, and only the pipeline's apply step touches
  the disk.
- **It is deterministic.** Same input, byte-identical output, on every platform and Node
  version. Sort with `compareCodepoint`; build paths with `joinPosix`, never `node:path`,
  whose `join` emits backslashes on Windows that would land in `Artifact.path` and hash into
  `state.json`. See [`determinism.md`](determinism.md).
- **It honours `isCanonicalSource`.** If the manifest names your artifact path as canonical
  input, emit nothing. `AGENTS.md` is the case this exists for: it is both a valid canonical
  source and the Codex adapter's output, and without the guard a repository using it as its
  source is one adapter away from having that source overwritten by itself.
- **It respects `manifest.options.marker`.** `withHtmlMarker` / `withHashMarker` add the
  generated-by comment where the format supports comments, and nothing where it does not.

Rules whose `globs` do not apply repo-wide need a decision. If the tool has a native
per-path mechanism — Copilot's `.github/instructions/*.instructions.md`, Cursor's `.mdc`
frontmatter — use it, and **split** rather than duplicate: Copilot applies a matching
path-specific file _in addition to_ the repo-wide one, so writing a rule to both sends it
twice. If the tool has no such mechanism, `renderConcatenated({ showGlobs: true })` states
the scope in prose (`**Applies to:** …`), which is documented lossy behavior rather than a
silent one.

## 5. `read`

`read()` turns the tool's native files back into canonical rules, and it is what
`driftgate init` uses to adopt a repository that has never used Driftgate. It must be
**lossless** — losing a line of somebody's instructions during import is the trust-fatal
failure this project rates highest.

```ts
async function read(ctx: AdapterContext): Promise<Partial<Canonical>> {
  if (isCanonicalSource(ctx.canonical.manifest, TOOL_MD)) return {};
  const contents = await ctx.fs.tryReadFile(TOOL_MD);
  if (contents === undefined) return {};
  return {
    rules: importConcatenated({ file: TOOL_MD, contents, headingLevel: 2, idFallback: 'tool' }),
  };
}
```

`importConcatenated` is two-tier, and the generated-by marker decides which tier applies. A
file Driftgate wrote is split at its headings — the exact inverse of `renderConcatenated`,
proved by a `write()` → `read()` round trip. A file it did not write is imported **whole**,
because in somebody's hand-written instructions a heading is prose structure rather than a
rule boundary, and splitting on it silently reorders their instructions and attaches the
wrong globs.

Guess nothing you cannot recover. `order`, `tools` and unknown frontmatter keys do not
survive rendering to a concatenated format, so return the defaults rather than inventing
values.

## 6. `docs` — the precedence data

This is the part of an adapter with value outside this repository. Incumbent tools already
sync files; nobody has written down what each tool truly loads. **Treat it as versioned
data, not comments.** `doctor` answers "which file wins, and what does it cost" entirely
from here, and every warning it prints is derived from this structure rather than from a
list of tools.

The scaffold's placeholders are deliberately wrong rather than plausible —
`https://example.com/…` and `1970-01-01` cannot be mistaken for a verified claim.

```ts
export const docs: AdapterDocs = {
  toolName: 'Gemini CLI',                  // the vendor's own name
  homepage: 'https://…',
  verifiedAgainst: { version: 'CLI docs as published 2026-09-02', date: '2026-09-02' },
  resolution: 'additive',                  // or 'override'
  files: [
    {
      pattern: 'GEMINI.md',                // POSIX, relative, literal or glob
      scope: 'project',                    // 'project' | 'global' | 'nested'
      role: 'instructions',                // 'instructions' | 'mcp' | 'skills' | 'settings'
      managed: true,                       // does Driftgate generate this path?
      nesting: 'all-merged',               // 'nearest-wins' | 'all-merged' | 'root-only'
      description: '…',
      source: { url: '…', title: '…', retrieved: '2026-09-02' },
    },
  ],
  limits: { maxBytesPerFile: 32_768, note: '…' },
  notes: [{ level: 'warn', message: '…', source: { … } }],
};
```

Three fields are easy to get wrong:

- **`files` order** means "highest precedence first" only under `resolution: 'override'`,
  where index 0 is the file that wins. Under `'additive'` every matching file is sent and
  the order ranks _specificity_, not authority.
- **`override` decides which file wins a conflict, not which file is sent.** Claude Code
  reads `CLAUDE.local.md`, `CLAUDE.md` and `~/.claude/CLAUDE.md` together while resolving
  conflicts by nearness. `doctor` models that with separate `loaded` and `shadowed` flags,
  and a shadowed file still costs its tokens.
- **`managed`** is your adapter's own claim, and only that. Copilot declares
  `managed: false` for `AGENTS.md` — meaning "not generated _for Copilot_" — while the Codex
  adapter very much generates it. `doctor` reconciles this across adapters; your job is to
  state your own claim accurately.
- **`retrieved` is the date you actually read the page.** Bumping it without re-reading
  turns the field into decoration, which is the one thing that would make this data
  worthless.

A `warn`-level `DocNote` is surfaced verbatim by `doctor`. Use it for the fact a user of
this tool would be surprised by — Copilot's three additive mechanisms are the model here.

`expectDocsValid` (run for every registered adapter by
`packages/cli/test/precedence-docs.test.ts`) checks source URLs, real calendar dates, the
`~/` ↔ `global` biconditional, POSIX non-absolute patterns, and — the strongest rule — that
every `managed` claim matches a golden fixture in both directions.

## 7. Test

The scaffold's three test files call the harness, which lives at
`@driftgate/adapter-kit/testing` — a separate entry point from the contract, because it
reads the filesystem and adapters must not.

| Helper                                       | Asserts                                        |
| -------------------------------------------- | ---------------------------------------------- |
| `expectFixtureMatch(tool, adapter)`          | `write()` matches the golden, byte for byte    |
| `expectIdempotent(tool, adapter)`            | ten renders produce one result                 |
| `expectImportMatch(tool, adapter)`           | `read()` matches the import golden             |
| `expectContentCovered(tool, adapter, files)` | import loses nothing                           |
| `expectDocsValid(adapter)`                   | the precedence data is well-formed             |
| `detectFixture(tool, 'positive')`            | a context over one of the detect fixture repos |

Never build a fixture subpath by hand; the helpers own the layout.

`pnpm build && pnpm fixtures:update` regenerates goldens after a deliberate change. It
writes nothing without `--yes`, refuses to run when `CI` is set, and deletes goldens the
adapter no longer produces.

**Mutate every new guard before believing it.** Delete the line your test protects and watch
that test — specifically that one — go red. This repository has found more than a dozen
tests that passed while catching nothing, and every one of them looked right.

## 8. Verify in the real tool, and say that you did

Install the tool, run `driftgate sync` in a repository it is configured for, and confirm the
generated file is actually loaded and actually obeyed. Record what you checked and against
which version in the PR, and put the version in `verifiedAgainst`.

A byte-exact fixture proves the adapter matches your reading of the documentation.
Only this step proves your reading was right.

## 9. Dogfood it

This repository generates its own agent config with every adapter it ships. Add your tool id
to `.driftgate/driftgate.yaml`, run `driftgate sync`, and commit the generated file with your
change. CI runs `driftgate check` here, so from then on your adapter's output is verified on
every push — including on Windows, which is where deterministic rendering breaks.

## Checklist

- [ ] Scaffolded, `pnpm test` green as generated
- [ ] `fixtures/<tool>/expected/` hand-written from the vendor's docs
- [ ] `detect` fixtures: positive detected, negative not
- [ ] `write` byte-exact and idempotent; glob-scoped rules split or stated
- [ ] `read` lossless; round trip passes
- [ ] `src/docs.ts` complete, every claim carrying a URL you read and a date
- [ ] Verified in the real tool, version recorded
- [ ] Added to `.driftgate/driftgate.yaml`, artifacts committed
- [ ] `pnpm verify` clean, and each new guard mutated once
